Этот проект следует принципам уважения и открытости. Мы ожидаем от всех участников:

## Как внести вклад

При создании issue об ошибке, пожалуйста, укажите:

- Версию браузера и ОС
- Шаги для воспроизведения

- Скриншоты (если применимо)

Мы рады новым идеям! В issue опишите:

- Проблему, которую решает ваше предложение
- Предлагаемое решение
- Альтернативные варианты, которые вы рассматривали

## Разработка

### Первоначальная настройка

```bash
# Клонируйте репозиторий
git clone https://github.com/iKonan-ru/card-holder.git
cd card-holder

# Установите зависимости
npm install

# Запустите dev-сервер
npm run dev
```

### Структура проекта

Проект следует архитектуре **Feature-Sliced Design**:

```
src/
├── app/        # Инициализация приложения
├── pages/      # Страницы
├── widgets/    # Композитные блоки
├── features/   # Функциональность
├── entities/   # Бизнес-сущности
└── shared/     # Переиспользуемый код
```

**Правила FSD:**

- Нижние слои не знают о верхних
- Используйте Public API (index.ts) для экспорта
- Избегайте циклических зависимостей

## Стиль кода

### TypeScript

- Всегда используйте строгую типизацию
- **Запрещено** использование `any`
- **Запрещено** приведение типов через `as` (используйте type guards)
- Интерфейсы начинаются с `I` (например, `IBankCard`)
- Типы начинаются с `T` (например, `TBankKeys`)

### Именование переменных

**Префиксы:**

- `is`, `has`, `can`, `should` - для boolean
- `get`, `convert`, `sort` - для утилит
- `checkIs`, `checkIf` - для type guards
- `create` - для фабрик
- `on` - для обработчиков событий
- `handle` - для обработки процессов
- `use` - для хуков
- `with` - для HOC

### Правила кода

1. **Нет литералов** - все числа/строки/массивы выносим в константы
2. **Логические конструкции** - используем `some`/`every` при >2 операторов
3. **Длинная логика в компонентах** - выносим в хук при >10 строк
4. **Колбэки** - выносим отдельно (кроме простого отрицания)
5. **Всегда блочные структуры** - даже для одной строки
6. **Запрещены сокращения** - пишем полные имена переменных
7. **Избегаем else** - если можно обойтись ранним return

## Тестирование

### Требования к тестам

- Каждая новая функция должна быть покрыта тестами
- Минимальное покрытие: 80%
- Используйте `describe` и `it` для структурирования
- Тесты должны быть читаемыми и понятными

### Запуск тестов

```bash
# Все тесты
npm test

# Watch режим
npm run test:watch

# С покрытием
npm run test:coverage

# UI для тестов
npm run test:ui
```

### Структура теста

```typescript
describe('ComponentName', () => {
  it('должен делать что-то конкретное', () => {
    // Arrange - подготовка
    const input = 'test';

    // Act - действие
    const result = someFunction(input);

    // Assert - проверка
    expect(result).toBe('expected');
  });
});
```

## Pull Request процесс

1. **Создайте ветку** от `main`:

   ```bash
   git checkout -b feature/your-feature-name
   ```

2. **Сделайте изменения** следуя стилю проекта

3. **Добавьте тесты** для новой функциональности

4. **Запустите проверки**:

   ```bash
   npm run fix      # Исправить стиль
   npm test         # Запустить тесты
   npm run build    # Проверить сборку
   ```

5. **Закоммитьте изменения**:

   ```bash
   git add .
   git commit -m "feat: добавить новую функцию"
   ```

   Формат коммитов:
   - `feat:` - новая функциональность
   - `fix:` - исправление ошибки
   - `docs:` - изменения в документации
   - `style:` - форматирование кода
   - `refactor:` - рефакторинг
   - `test:` - добавление тестов
   - `chore:` - обновление зависимостей, конфигурации

6. **Создайте Pull Request** с описанием:
   - Что изменено и почему
   - Связанные issue (если есть)
   - Скриншоты (для UI изменений)

### Чеклист для PR

- [ ] Код следует стилю проекта
- [ ] Добавлены/обновлены тесты
- [ ] Все тесты проходят
- [ ] Линтер не выдает ошибок
- [ ] Обновлена документация (если нужно)
- [ ] Нет breaking changes (или они описаны)
