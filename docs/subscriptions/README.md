# Card Holder — Функциональность «Подписки»

> Продуктово-технический дизайн-документ. Сопровождается визуальным концептом с макетами:
> [`concept.html`](./concept.html) (открыть в браузере).

Документ описывает расширение Card Holder от хранилища банковских карт до приватного
менеджера подписок. Он покрывает анализ рынка, продуктовое видение, модель данных,
наложение на текущую FSD-архитектуру и детальный поэтапный план реализации.

**Важно:** приложением пока никто не пользуется, данных нет — работаем «с чистого листа».
Наследственность и версионность БД не сохраняем: `onupgradeneeded` дропает и пересоздаёт
хранилища, версию просто поднимаем 6 → 7.

**Статус решений:** продуктовые развилки согласованы с владельцем продукта — см. раздел 6.
Документ отражает уже принятые решения, а не варианты.

## 1. Анализ рынка и позиционирование

Рынок трекеров подписок делится на два лагеря:

| Приложение                     | Модель                    | Как находит подписки                         | Приватность                              | Слабое место                                    |
| ------------------------------ | ------------------------- | -------------------------------------------- | ---------------------------------------- | ----------------------------------------------- |
| **Rocket Money** (ex-Truebill) | Автосинк с банком         | Автоматически из транзакций                  | Данные в облаке, нужен банковский доступ | Платно, США-центрично, требует доверия к облаку |
| **Bobby**                      | Ручной ввод               | Руками, каталог сервисов                     | Локально                                 | Не знает карту оплаты, нет умных подсказок      |
| **Subby / SubTrack**           | Ручной ввод               | Руками + напоминания                         | Локально                                 | Оторван от реальных карт пользователя           |
| **Card Holder (мы)**           | Ручной ввод + карты рядом | Руками, каталог + **привязка к своей карте** | Зашифровано, offline                     | —                                               |

### Наши устойчивые преимущества (moats)

1. **Связь «подписка ↔ карта».** Мы уже храним карты пользователя. Значит, можем связать
   подписку с конкретной картой и ходить по этой связи в обе стороны. Ни Bobby, ни Subby
   этого не умеют — у них нет карт.
2. **Сценарий смены карты.** Потеряли/перевыпустили карту → показываем чек-лист подписок,
   которые нужно перепривязать. Реальная боль, которую на рынке никто не закрывает.
3. **Приватность как продукт.** Всё шифруется AES-GCM и живёт только в браузере (IndexedDB).
   Никакого банковского доступа и облака — ценность Bobby, но с «умом» Rocket Money.

**Вывод по позиционированию:** мы играем в лагере ручных приватных трекеров (как Bobby),
но снимаем их ключевое ограничение за счёт того, что карты уже в приложении.

## 2. Продуктовое видение

### 2.1. Что показываем в подписке

**База (из исходного запроса):**

- Логотип + название сервиса
- Сумма + валюта списания
- Период списания (нед. / мес. / кв. / год / произвольный)
- Дата следующего списания
- Внешняя ссылка на страницу управления подпиской
- Категория сервиса

**Способ списания (обязательное поле):**

Подписка всегда указывает, **как** с неё списывают деньги. Это не только карта:

- **Карта** — ссылка на сохранённую карту (наш дифференциатор, см. ниже)
- **Мобильный платёж / SMS** — списание с баланса телефона
- **Наличные**
- **Электронный кошелёк** (ЮMoney, и т.п.) — с текстовой меткой
- **Другое** — с текстовой меткой

Карта — опциональна, а вот способ списания — обязателен. Если выбрана карта, включается
весь «карточный слой» ниже; для остальных способов показывается просто чип метода.

**Умный слой (лучшие практики рынка):**

- **Обратный отсчёт** до списания («через 3 дня»), с цветовой индикацией срочности
- **Нормализация стоимости**: ₽599/мес → ₽7 188/год
- **Итоги**: суммарные траты в месяц и в год (раздельно по валютам, без конвертации)
- **Статус**: активна / пробный период / на паузе / отменена
- **Пробный период**: дата окончания + подсказка «успеть отменить»
- **«С вами N месяцев»** и всего потрачено с даты первой оплаты
- **Изменение цены** (↑ подорожало) и выгода перехода на годовую оплату
- **Напоминание** за N дней до списания

**Карточный слой (уникально для нас, когда способ = карта):**

- Маскированная карта •• 1234 в цвете карты прямо в строке списка
- Блок «Подписки на этой карте» на экране карты + сумма списаний с карты
- Чек-лист миграции при смене/перевыпуске карты
- Группировка/фильтрация подписок по карте

### 2.2. Реальные напоминания о списаниях

Согласовано: делаем **настоящие push-уведомления**, а не только внутриэкранную сводку.

**Инженерная честность про offline-PWA без сервера.** Классический Web Push (сервер →
устройство при закрытом приложении) требует бэкенда с VAPID и внешних запросов — а у нас
нет сервера и мы не ходим в сеть. Поэтому «реальные push» реализуем как **локально
запланированные уведомления**, которые не требуют сервера:

- **Notification Triggers API** (`showTrigger` + `TimestampTrigger`) — планируем уведомление
  на точную будущую дату списания; браузер сам покажет его локально. Основной механизм.
- **Periodic Background Sync** — Service Worker периодически просыпается и до-планирует/
  проверяет ближайшие списания. Резервный механизм «пробуждения».
- **Внутриэкранный баннер** «Ближайшие списания» + бейдж на табе — универсальная база,
  работает всегда и везде, даже там, где системные уведомления недоступны.

Надёжность фоновой доставки при полностью закрытом приложении зависит от браузера
(лучше всего — установленный PWA на Chromium; в Firefox/Safari — деградация до баннера).
Запрашиваем разрешение на уведомления в подходящий момент (не на старте). Настоящий
серверный push — отдельный трек, если появится бэкенд (см. раздел 7).

### 2.3. Навигация

Сегодня приложение одностраничное (сетка карт + FAB + выезжающая панель), без навигационной
оболочки. Вводим **нижний таб-бар**: `Карты · Подписки · Обзор`.

- Нативно для установленного PWA, масштабируется на будущие разделы.
- На десктопе таб-бар превращается в боковой рельс / верхние табы.
- FAB и панели переезжают внутрь своих страниц.

## 3. Модель данных

Чистый лист — без миграций. Производные значения (следующая дата списания, месячный
эквивалент, дни до списания) **не храним**, а вычисляем чистыми функциями.

Сервис и категория — **пользовательские справочники** (как `owners` и `card-types` в текущем
приложении): отдельные зашифрованные сторы, изначально пустые, наполняются на лету из формы.

```ts
// entities/subscription/types/types.ts
import type { IBankCard } from '@entities/bank-card';

export type TBillingUnit = 'day' | 'week' | 'month' | 'year';
export type TSubStatus = 'active' | 'trial' | 'paused' | 'canceled';

export interface IBillingCycle {
  interval: number; // 1, 3, ...
  unit: TBillingUnit;
}

// Способ списания — обязателен; карта — лишь один из вариантов.
export type TPaymentMethodType = 'card' | 'sms' | 'cash' | 'wallet' | 'other';

export interface IPaymentMethod {
  type: TPaymentMethodType;
  cardId?: IBankCard['id']; // только при type === 'card' → включает карточный слой
  label?: string; // метка для wallet / sms / other («ЮMoney», «+7 903…»)
}

export interface ISubscription {
  id: string;
  order: number; // как у карт — для DnD-сортировки
  name: string;
  serviceId?: string; // ссылка на пользовательский справочник сервисов
  categoryId?: string; // ссылка на пользовательский справочник категорий
  amount: number;
  currency: string; // ISO-4217: 'RUB', 'USD' — без конвертации
  billingCycle: IBillingCycle;
  anchorDate: string; // ISO-дата известного списания → считаем график
  status: TSubStatus;
  paymentMethod: IPaymentMethod; // ← обязательно
  manageUrl?: string; // внешняя ссылка на управление
  reminderDaysBefore?: number;
  trialEndsAt?: string;
  startedAt?: string; // для «с вами N мес» и «всего потрачено»
  notes?: string;
  color?: string; // переопределение цвета
}
```

```ts
// entities/service/types — пользовательский справочник, изначально пустой
export interface IService {
  id: string;
  name: string;
  color?: string; // брендовый цвет; фолбэк — цветная монограмма
  logo?: string; // опц. загруженное изображение как data-URI (хранится в шифрованном пейлоуде)
  defaultManageUrl?: string; // подставляется в новую подписку этого сервиса
  defaultCategoryId?: string;
}

// entities/subscription-category/types — пользовательский справочник, изначально пустой
export interface ISubscriptionCategory {
  id: string;
  name: string;
  color?: string;
  icon?: string; // опционально
}
```

### 3.1. Хранение (IndexedDB + шифрование)

- Три новых object store: `subscriptions`, `services`, `subscription-categories`
  (keyPath `id`; для `subscriptions` — индекс `order`).
- `DATABASE_VERSION`: 6 → 7. `onupgradeneeded` уже дропает/создаёт сторы — миграции не нужны.
- Шифрование **переиспользуем как есть**: `encryptRecordFields<T>` / `decryptRecordFields<T>`
  из `shared/lib/crypto/at-rest.ts` (тот же генерик-паттерн, что у `owners`/`card-types`).
  `id` (и `order` у подписок) открыты для индексации, остальное — в зашифрованном
  `encryptedPayload` (AES-GCM 256). Логотип сервиса (data-URI) тоже попадает в шифропейлоуд.

### 3.2. Движок расписаний (чистые функции, `shared/lib/subscriptions`)

Всё покрывается юнит-тестами (планка проекта > 90%).

- `getNextChargeDate(anchorDate, cycle, now): Date` — продвигает `anchorDate` на шаг цикла,
  пока не станет `>= now`.
- `getUpcomingCharges(subs, withinDays, now): UpcomingCharge[]` — ближайшие списания,
  отсортированные по дате (для баннера, планирования уведомлений и календаря).
- `toMonthly(amount, cycle): number` / `toYearly(amount, cycle): number` — нормализация.
- `getMonthlyTotalsByCurrency(subs): Record<string, number>` — итоги **раздельно по валютам**,
  без конвертации.
- `getTotalPaid(sub, now): number` — всего потрачено с `startedAt`.

### 3.3. Справочники (пользовательские)

Осознанно **без встроенного каталога** — наполняется вручную, изначально пусто.

- **Сервисы** (`entities/service` + `features/services-management`) — зеркало
  `owners`/`card-types`: свой стор, свой select-с-созданием на лету. Опциональный логотип —
  загружаемое изображение (data-URI), фолбэк — цветная монограмма из `name` + `color`.
- **Категории** (`entities/subscription-category` + `features/categories-management`) —
  точно тот же паттерн: свой стор, создание из формы, цвет/иконка.
- Никаких `services-config` / `categories-config` в `shared/data` не заводим.

## 5. Поэтапный план реализации

Семь этапов, каждый — самостоятельный вертикальный срез с рабочим результатом и критерием
приёмки. Порядок снимает риски: сперва структурный сдвиг (навигация), затем данные и
справочники, затем UI, потом связи, уведомления и аналитика.

### Этап 0 — Каркас и навигация

**Цель:** ввести навигационную оболочку (самое рискованное структурное изменение — первым).

- Виджет `app-nav` — таб-бар; на десктопе — боковой рельс/верхние табы.
- Рефактор `main-page` → `cards-page`; пустые `subscriptions-page`, `overview-page`.
- Лёгкий стор навигации (Zustand, persist активного таба).
- FAB и панели переезжают внутрь своих страниц.

**Готово, когда:** переключение табов работает, карты функционируют как раньше, тесты и
покрытие зелёные.

### Этап 1 — Данные, справочники и ядро

**Цель:** фундаментальный слой данных, полностью под тестами.

- Сущности `subscription`, `service`, `subscription-category` + типы (`ISubscription`,
  `IBillingCycle`, `IPaymentMethod`).
- IndexedDB: три стора, версия 7, CRUD поверх генерик-шифрования.
- Сторы (Zustand): `subscriptions-store` (зеркало `cards-store`), сторы справочников
  сервисов и категорий (зеркало `owners`/`card-types`).
- Чистые функции `lib/subscriptions`: `getNextChargeDate`, `getUpcomingCharges`, `toMonthly`,
  `toYearly`, `getMonthlyTotalsByCurrency`.

**Готово, когда:** CRUD подписок/сервисов/категорий работает (проверяемо), даты списаний
считаются верно, юнит-тесты зелёные.

### Этап 2 — CRUD-интерфейс

**Цель:** первый осязаемый результат — подписками можно управлять из UI.

- `subscription-form` (модалка add/edit/delete) на паттернах `card-form`.
- **Поле «Способ списания»** (обязательное): карта из сохранённых · SMS · наличные · кошелёк ·
  другое; для карты — селект карты, для кошелька/другого — текстовая метка.
- Селекты **сервиса** и **категории** с созданием на лету (пустой справочник → «+ Создать»),
  по образцу модалок владельца/типа карты.
- `subscription-list` + богатая строка `subscription-row` (лого/монограмма, чип способа
  списания, статус, отсчёт).
- Пустое состояние + FAB «Добавить подписку».

**Готово, когда:** пользователь создаёт сервис/категорию на лету, добавляет/редактирует/
удаляет подписку, задаёт способ списания, видит её в списке.

### Этап 3 — Детали и связи с картой

**Цель:** оживить главный дифференциатор — связь подписка ↔ карта в обе стороны.

- `subscription-detail`: нормализация цены, «с вами N мес», напоминание, заметки, чип способа.
- Внешняя ссылка «Управлять ↗»; для способа = карта — внутренний переход «Открыть карту».
- `card-subscriptions-link`: блок «Подписки на этой карте» + сумма списаний с карты.
- Баннер миграции «Перевыпустили карту? Обновите подписки».

**Готово, когда:** из подписки с картой открывается карта и наоборот; на карте виден список
её подписок и сумма списаний; для не-карточных способов корректно показывается чип метода.

### Этап 4 — Реальные уведомления + сводка на входе

**Цель:** настоящие локальные push + универсальная внутриэкранная база.

- `features/notifications`: запрос разрешения в подходящий момент; UX включения.
- Планирование локальных уведомлений: **Notification Triggers API** (`TimestampTrigger`)
  на дату списания; **Periodic Background Sync** для до-планирования; проверка поддержки и
  graceful degradation.
- Кастомный Service Worker через `vite-plugin-pwa` (`injectManifest`): `notificationclick`
  (открыть нужную подписку), `periodicsync`.
- Внутриэкранный баннер `upcoming-charges` вверху главной + бейдж-счётчик на табе «Подписки».
- Представление «Календарь / скоро»; пробные периоды — «успеть отменить до …».

**Готово, когда:** при поддержке браузером приходит системное уведомление к дате списания;
везде работает баннер-сводка и бейдж; клик по уведомлению открывает подписку.

### Этап 5 — Контроль вида и аналитика

**Цель:** обобщить инфраструктуру вида карт на подписки + экран «Обзор».

- Sort / filter / group для подписок (переиспользуем `card-view`-паттерн).
- Группировка по категории, **по карте** и по способу списания.
- `overview-page`: итоги месяц/год **раздельно по валютам**, траты по категориям, календарь.
- Экспорт/импорт расширяем на подписки, сервисы и категории (в существующий формат бэкапа).

**Готово, когда:** список сортируется/фильтруется/группируется; обзор показывает верные
итоги по каждой валюте; бэкап включает подписки и справочники.

### Этап 6 — Полировка и расширения

**Цель:** довести до продакшн-качества.

- История цен и индикатор подорожания (↑), подсказка выгоды годовой оплаты.
- DnD-сортировка подписок (переиспользуем `@dnd-kit`).
- Загрузка/замена логотипа сервиса (data-URI), редактирование справочников.
- i18n-копирайт, доступность, покрытие тестами > 90%.

**Готово, когда:** выбранные расширения включены без регрессов; сборка, линт, тесты зелёные.

## 6. Подтверждённые продуктовые решения

| Вопрос           | Решение                                                                                                                           |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Навигация        | **Нижний таб-бар** (Карты · Подписки · Обзор); на десктопе — боковой рельс.                                                       |
| Напоминания      | **Реальные push** — локально запланированные уведомления (Notification Triggers + Periodic Sync) + баннер как база.               |
| Мультивалютность | **Да, без конвертации.** Итоги раздельно по валютам. Локальная таблица курсов отклонена (устаревает), внешних запросов не делаем. |
| Категории        | **Пользовательский справочник** (паттерн owners/card-types), изначально пустой.                                                   |
| Каталог сервисов | **Пользовательский справочник**, наполняется вручную, изначально пустой; логотип — загружаемое изображение, фолбэк — монограмма.  |
| Способ списания  | **Обязателен.** Карта опциональна; варианты: карта · SMS/моб. платёж · наличные · кошелёк · другое.                               |

### Производные решения (дефолты, принятые в рамках согласованного)

- **Способы списания (enum):** `card` · `sms` · `cash` · `wallet` · `other`; для `wallet`/`other`/`sms`
  — опциональная текстовая метка. Список расширяем при необходимости.
- **Логотип сервиса:** опциональное загружаемое изображение (data-URI, шифруется вместе с записью);
  без сети. Фолбэк — цветная монограмма из названия.
- **Push:** реализуем лучший доступный локальный механизм (см. 2.2); доставка при закрытом
  приложении — best-effort и зависит от браузера. Разрешение запрашиваем не на старте.

## 7. Что осознанно вне рамок

- **Конвертация валют** — отклонена: локальная таблица даёт устаревшие данные, внешних
  запросов не делаем. Показываем итоги раздельно по валютам.
- **Серверный Web Push** (VAPID) — нужен бэкенд и внешние запросы; противоречит offline-принципу.
  Возможен отдельным треком, если появится сервер.
- **Автоопределение подписок из банковских транзакций** — нет банковского доступа, и это
  принципиально ради приватности.
- **Переговоры об отмене/возврате** (фича Rocket Money) — требует бэкенда и человека.
- **Синхронизация между устройствами** — приложение локальное; возможна через зашифрованный
  экспорт/импорт как отдельный трек.
